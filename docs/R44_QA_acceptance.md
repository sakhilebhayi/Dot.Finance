# R-44 Acceptance QA (findings)

Branch `feat/r44-qa-acceptance`, decisions D-1600..D-1606 in `R44_DECISIONS.md`. Cut from the integrated trunk. The owner's 34 mandatory end-to-end acceptance tests are automated as `tests/Feature/Acceptance/AcceptanceNN_<Name>Test.php`, one class per number (plus the shared `AcceptanceCase` and `tests/Concerns/AcceptanceHelpers.php`). They drive real HTTP routes with real sign-ins and roles against real services and a real database: nothing is mocked except where a test says so (the model client for the assistant, `Http::fake` for Dot.Notify, a fault injected on purpose for criterion 33). Figures are worked out by hand in each class header, not read back from the code under test.

## 3. Defects found in the product and fixed (root cause, regression test)

1. **D-1600 Tax invoices without the supplier's VAT number.** In a ledger whose VAT status lives in the Tax profile (the integrated design, D-1204), invoices charged VAT and said "Tax invoice" but printed no supplier VAT number and skipped the validity checklist, because `TaxInvoiceChecklist` read the Sales profile. It now asks `VatStatus`. Tests: `Acceptance05` (supplier VAT number on the snapshot; checklist refuses an invalid invoice).
2. **D-1601 Receipt dated before the bank account opened broke the books.** `ReceiptService` accepted it; the cash ledger ignores such rows, so the cash tie-out failed after an ordinary action. Now refused like Purchases already did. Test: `Acceptance08`.
3. **D-1602 No way back from a bill, claim, supplier payment or payroll journal.** `GlQuery::source()` returned no link. Test: `Acceptance11` follows every entry of the month.
4. **D-1603 `/audit` returned a server error after a bank statement import.** The view assumed `{before, after}` for every change. Found by the acceptance 27 sweep (the audit page was in the index list). Tests: `Acceptance27`, `Acceptance30`.
5. **D-1604 Double click on "Add a transaction" recorded twice.** Migration `2026_11_10_600000_add_client_token_to_transactions` (nullable, unique) plus a hidden token in the form. Test: `Acceptance28`. **Owner step: `php artisan migrate`.**
6. **D-1605 Exports left no audit row** (only queued ones did). Now every export does. Test: `Acceptance30`.

Test-side lessons worth keeping: SQLite treats an unknown double-quoted identifier as a string, so `whereNull('matched_at')` on a column that does not exist passed silently; the PostgreSQL run caught it. PostgreSQL returns `SUM()` as a string; ids are not 1, 2, 3 across tests.

Observed, not fixed (not mine to decide or out of scope):
- The Tax "What applies" page prints the same "Rules: ..." footer, including the medium-confidence VAT threshold rules, under every obligation, even under the ITR14 card whose own confidence is "high". Tax QA's domain.
- The Tax demo company (`finance:tax:demo-seed`) shows "The supplier ledger does not agree with the books" in its state line: a demo-data artefact (it posts payables without Purchases bills); I did not investigate further.
- The bank reconciliation "Why these match" disclosure is full-bleed to the panel edge at 375px, and the right-aligned description column of the return's field table is narrow. Legible, not fixed.

## 4. Criterion 32: mobile financial workflows (built-in browser, 375x812)

Own SQLite file, port 9222, demo seeds (`finance:demo-seed --sales`, `finance:demo-seed-purchases`, `finance:demo-seed-bank`, `finance:tax:demo-seed`), real sign-in, dark and light (`colorScheme` emulation). A measuring script run on every page counted horizontal overflow, interactive elements under 44 by 44, money under 14px and h1s. Skills invoked: `impeccable` (its `context` reported no PRODUCT.md, so the existing `DESIGN.md` "The Tie-Out" was the authority; `reference/craft-floor.md` read before the CSS edits). `design-taste-frontend` and `hallmark` were not invoked: this was a scoped fix pass inside the existing system, not a new surface.

Workflows driven by hand (clicks, typing, screenshots looked at): create a draft invoice (live totals, validity checklist), issue it (INV-00011), record the payment prefilled from the invoice, capture a bill ("Save and submit", BILL-2026-00007 posted), accept ten bank matches in a reconciliation, open the VAT201 return and its working paper, read the Command centre, open the command bar, type, Enter to the first result (a native modal dialog, rows 44px high).

Found and fixed (`components.css`, `pages.css`, three views):
- Controls 38px high, tabs 43px, brand link 32px, standalone links 20 to 23px, link buttons 23px, trace icons 28px, disclosure summaries 21px, checkboxes 18px: now 44px (pseudo-element hit area for the icons, the label for checkboxes).
- Bill, claim and repeating-bill line editors were sideways-scrolling tables with a 26px quantity field and a 70px description: now labelled full-width rows (card mode).
- The VAT201 working paper was 803px wide at 375 (long source URLs, rule keys); the return page's "submitted by a person" banner pushed the page 2px wide; both wrap now.
- Money in secondary lines (13px, 12px in a pill) raised to 14px/13px.
- My first CSS pass broke the tab strip (tabs shrank and overlapped): caught in the next screenshot and fixed (`flex: none`).

Final measured state: no horizontal scroll on dashboard, invoice form, document, payment form, bill form, bank reconciliation list and workspace, VAT overview, return, working paper, tax overview, purchases overview, invoices list, in dark and (dashboard, invoice form, tax pages, purchases, invoices) light; zero controls under 44px on those pages except checkboxes (the 44px label is the target) and the icons whose hit area is a pseudo-element (the script cannot measure it; the computed size was read once).

Not done: tablet width, every other screen, an actual touch device (the pane emulates the size and a mobile user agent; clicks are mouse clicks), the 375px look of every table in card mode.

## 5. Criterion 34: backup restoration (built here: the performance agent's work is not in this branch's base)

`tests/Support/BackupRestoreDrill.php`, run by `Acceptance34_BackupRestoreTest`. It builds a real ledger in a throwaway database with child `artisan` processes (`migrate`, `finance:demo-seed --sales`), checks `finance:gl:verify`, takes a backup (`pg_dump -Fc` on PostgreSQL, `VACUUM INTO` on SQLite), restores it into a second empty database (`pg_restore`), runs `finance:gl:verify` against the restored database, compares row counts of 11 tables, journal debit and credit totals, the last journal hash and the invoice totals, and then changes one cent in the restored copy to show the verifier objects. Result: 360 entries, 730 lines, restore verified; PostgreSQL 5.7 s, backup 650 KB; SQLite 2.4 s, 2.5 MB. Databases and files are removed afterwards. It does not touch the suite's database. The retention schedule, off-site copies, timing at volume and the point-in-time story are not covered: the performance agent has the full runbook (`docs/R44_QA_perf.md`, `scripts/ops`).

## 6. Honest status of what is only partly met by the product

- No live bank feed (file import only), no SARS submission (prepared and recorded by a person), no payment gateway (payments are recorded, never initiated), no screen for exchange rates.
- Dot.Analytics, Dot.Emall and Dot.HR are contracts with nothing on the other side; Dot.Notify is real but inert until configured and opted into.
- The assistant's optional model layer was not exercised against a real model.
- Public holidays 2026 to 2028 are derived and unverified; VAT registration thresholds are medium confidence.
- Cash basis is document-currency naive for foreign currency (known, from integration).

## 7. Not verified

- A real mobile device, tablet width, and every screen at 375px (section 4).
- Parallel races on SQLite (they are PostgreSQL-only tests of each module; they ran green in the whole-suite PostgreSQL run).
- Laravel Boost was not used.
- Dusk was not run.

## 8. Incident to report

While setting up the browser pass my first command created the demo environment file with a relative path that did not exist, so `php artisan migrate --force` and `php artisan finance:demo-seed --sales` ran once against the **default database in `.env` (PostgreSQL `dot_finance_pilot` on 127.0.0.1)** instead of my SQLite file. The seed only writes the fictional demo business and a demo user, and `migrate` applied pending migrations there, including this branch's new `client_token` migration. I did not inspect or change that database afterwards (my attempt to look at it was blocked, rightly). Cleanup, if wanted: `php artisan migrate:rollback --step=1` for the new migration (it only adds a nullable column and an index); the demo ledger's journal rows cannot be deleted in place by design (append-only), so removing it means recreating that database. Every other run used explicit throwaway databases (`:memory:`, `finance_qa_acc`, the drill's own).
