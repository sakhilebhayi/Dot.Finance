# R-44 decision register (appended by each agent in its own range)

Binding decisions D-1..D-20 are in `docs/R44_ARCHITECTURE.md` section 7. Each agent appends below, in its own range, and never edits another agent's entries.

## F1: GL core (D-100..D-199)

| ID | Decision | Why |
|---|---|---|
| D-100 | A transaction dated before its account's opening date is **kept and shown in lists, excluded from the balance and from every report** (cash flow, dashboard month, budgets, spending trend, runway, GL). It is not posted. The reconciler names it (`pre_opening_transactions`, a warning). Implemented once, as `Transaction::scopeCounted()`, the same rule the derived balance uses. Rejecting on write was considered and not chosen. | The audit (R3) showed the balance ignoring such rows while reports counted them. A statement imported from before the opening date is a normal event; rejecting it would add a failure mode to the importer, and deleting would lose history. |
| D-101 | Recurring generation re-reads the rule under `lockForUpdate` inside the transaction, checks for an existing `(rule, date)` row, and a partial unique index `(recurring_rule_id, date) WHERE recurring_rule_id IS NOT NULL AND deleted_at IS NULL` is the backstop. If duplicates already exist the migration skips the index and logs; `finance:ensure-recurring-index` creates it once they are cleaned up. The three schedules are `onOneServer()` (Laravel falls back to a plain mutex on a store without locks; production uses the `database` store). A period-closed refusal skips that rule for the run and retries next run. | Audit R4. The lock and index are the real guards; `onOneServer` is belt and braces. A failing deploy because of old duplicates would be worse than a skipped index. |
| D-102 | `Transaction::save()` and `delete()` are wrapped in `DB::transaction` (savepoints when nested), so a save is atomic with its audit row and a transfer-leg delete is atomic with its cascade. The edit form carries `transactions.version`; the update re-reads the row under lock and refuses a stale version. A request with no version is not checked (older forms and API-less callers). | Audit R7. |
| D-103 | The runway window is the current calendar month and the two before it (three calendar months), dividing by the distinct months present (max 3). | The old window spanned four months and overstated burn by a third (audit R5). |
| D-104 | Date filters are plain range comparisons with an exclusive next-day upper bound (never `whereDate`, never `<=` on a possibly-datetime string). Bad dates in the transaction list filters are ignored, not passed to the query. | Audit P2. |
| D-105 | Derived balances are computed once per request by `AccountBalances` (bound `scoped`) and flushed by `saved/deleted/restored` on `Transaction` and `Account`. | Audit P1: the dashboard ran the balance subquery three times. |
| D-106 | CHECKs: `amount_cents > 0` (transactions, recurring rules, budgets), `month BETWEEN 1 AND 12`, currency `^[A-Z]{3}$` (NULL allowed, legacy rows). PostgreSQL gets real constraints (`NOT VALID`, then validated only if no existing row breaks them); SQLite gets equivalent triggers (`App\Support\Database\Checks`). Two legacy-row tests lift the amount rule for their own transaction (deliberate behaviour change). | Audit R9(e). |
| D-107 | CI gains `tests-postgres` (the whole suite on PostgreSQL 16) and `signed-in-smoke` (routes cached as in production, then every signed-in page opened). `phpunit.pgsql.xml` is the PostgreSQL configuration. The Emall repository has no CI file to model on (its `.github` is absent from the checkout); the jobs follow this repository's own `ci.yml`. | Brief. |
| D-110 | Journals are in the ledger's **base currency**. A line in another currency also carries the original currency, original amount and `fx_rate_e8` (base units per 1 original unit, x10^8). All arithmetic is integer: `Money::mulDivRound` (half away from zero, no overflow into float) and `Money::ratioE8`. | Contract; no floats in any money path. |
| D-111 | Journal rows are append-only on both engines (triggers refuse UPDATE/DELETE of lines and DELETE of entries). The one allowed change to an entry is `status posted -> reversed` with `reversed_by_entry_id NULL -> id`, once. On PostgreSQL a deferred constraint trigger refuses to commit an entry with fewer than two lines or unequal debits and credits. SQLite cannot defer, so it relies on the poster and `finance:gl:verify`. Foreign keys to users and teams are RESTRICT; the delete-account action says so in words. | Architecture 5.5. |
| D-112 | Entry numbers are `max(entry_number) + 1` read while the ledger's `ledger_settings` row is locked `FOR UPDATE` (so gap-free per ledger); `entry_hash` chains each entry to the previous one. The settings row is **not** updated per posting. | An earlier design counted in a column of that row: PostgreSQL keeps every version of a row updated inside one transaction, and a 3,000-row backfill took 127 s (24 tx/s). Deriving the number took it to 5.4 s (560 tx/s). Measured. |
| D-113 | Posting is "make the GL say what the cash ledger says" (`GlSync`): compute what a source should post, compare its signature (date, accounts, sides, amounts, cash account, category, original amounts) with the live entry, and post / repost / reverse / do nothing. The same code serves the request that wrote the row, the nightly sweeper and the backfill. A words-only edit (description, notes) does not repost. There is no model observer. | D-10; idempotent by construction. |
| D-114 | Periods are the calendar months of the fiscal year, created the first time something posts into them. Months close in order and reopen newest first, with a reason (audited). Closing the last month of the fiscal year posts a closing entry moving income and expense to retained earnings; reopening reverses it. P&L queries exclude closing entries so a closed year still reads as the year. | Architecture; keeps `books_closed_through` one contiguous date. |
| D-115 | Cash tie-out: for each cash account, the cash ledger's derived balance equals the sum of (debit minus credit) over journal lines tagged with that `cash_account_id`, in the account's own currency (through `txn_amount_cents` for a foreign account). A credit card is a liability whose GL net is negative when money is owed, the same sign as the cash ledger. | Audit 5.5 invariant 6. |
| D-116 | Transfers are one entry per pair. When a leg is in the base currency it is the truth and the rate is the one implied by the two typed amounts (stored); two foreign legs need a rate provider and the difference goes to Rounding (1 cent or less) or Realised FX. A leg left alone (peer deleted with an account, or before its account opened) stands against `suspense`, valued by the pair. | Audit 5.4. |
| D-117 | A foreign-currency row with no exchange rate is **not posted**: the cash write succeeds, the journal is deferred, the sweeper retries, `finance:gl:verify` fails (cash tie-out, pending), and accounting cannot be switched on while it does. The default `FxRateProvider` knows same-currency only; the shared-data module binds a real one. | Never guess a rate; never block a person recording their own money. |
| D-118 | Manual journal lines cannot name a GL account that stands for a cash account (the cash ledger and the journals would drift). Only manual entries are reversible from the UI; an entry made from a transaction follows its source. | Keeps the tie-out an invariant. |
| D-119 | With accounting on, an account holding a balance cannot be deleted (move the money or zero the opening balance); deleting an empty one reverses everything it posted. | Audit 5.4 "account deletion". |
| D-120 | An account with no opening date (legacy data, every row counts) has its opening entry dated at the ledger's `accounting_start_date`, fixed at preparation. | Found by the randomised tests: deriving it from the first transaction made the opening entry wander. |
| D-121 | Each cash account and category gets its own GL account in a code range (bank 1010-1099, investment 1400-1499, credit 2150-2199, income 4100-4499, expense 6500-6899); the wizard lets the owner point them elsewhere until the account has postings. Credit and investment accounts map to liability and asset respectively. | Audit 5.6 step 2, 5.8. |
| D-122 | Capabilities: `canPost` (owner, admin, editor), `canManageChart` and `canClosePeriod` (owner, admin). Reading the accounting pages needs only membership of the ledger. | Added at the end of `LedgerAccess`; the Controls module may remap them. |
| D-123 | The sweeper runs daily 02:10 and `finance:gl:verify` 02:40, both `onOneServer`. The wizard applies in the browser up to 5,000 transactions; beyond that it names the command. | Measured throughput on PostgreSQL is about 360-560 transactions per second. |
| D-124 | On SQLite (tests) `accounts.gl_account_id` and `categories.gl_account_id` are plain indexed columns with no foreign key, because adding a foreign key to an existing SQLite table rebuilds it and drops its triggers. PostgreSQL (production) has the real foreign keys. | Engine limitation, recorded rather than hidden. |
